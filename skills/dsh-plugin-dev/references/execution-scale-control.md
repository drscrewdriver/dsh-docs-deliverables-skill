# 执行资源规模控制（六面）

## 0. 什么时候需要看这一篇

插件只要出现下面任一形态，就已经站在这一篇的题上：

- 一次要处理「很多条」或「很长一段」（抽取、蒸馏、压缩、批量嵌入、扫盘、重建索引）
- 有后台填充与前台请求共存（后台任务会把用户轮次卡住）
- 有重依赖（模型推理、远端服务、原生库），会慢、会失败、会崩
- 会调用 LLM（成本与超时都是规模函数）

反面：纯 UI 插件、单次 O(1) 查询、无外部依赖的事件钩子——不需要。

---

## 1. 全景：六个控制面

| # | 面 | 解决的问题 | 一句话口径 |
|---|---|---|---|
| **F1** | **分批 / 分块（batch & partition）** | 单次调用太大 → 超时、prompt 爆炸、失败半径过大 | **按规模切块，失败半径 ≤ 一块** |
| **F2** | **隔离（isolation）** | 同进程冲突、同步调用冻结事件循环、崩了拖死宿主 | **原生重活一律出进程** |
| **F3** | **自愈（respawn / degrade）** | 崩一次就停摆到重启 | **有界重启或降级：不许无限重试** |
| **F4** | **压力控制（熔断 / 退避 / 预算）** | 慢依赖拖垮写入；反复撞同一堵墙 | **快失败 + 降级 + 有界重试** |
| **F5** | **队列与优先级（queueing）** | 后台填充堵塞用户请求 | **前台永远优先，后台可被插队** |
| **F6** | **预算留痕与观测（budget & observability）** | 越界后无法追责/复现 | **每个越界都要留可核对的数** |

> 记忆锚：**F1 决定「一次处理多少」，F2 决定「在哪处理」，F3 决定「坏了怎么活」，F4 决定「慢了怎么退」，F5 决定「谁先跑」，F6 决定「事后能不能证明」。**

---

## 2. 每面的不变量

| 面 | 不变量（违反了就是债，不是性能） |
|---|---|
| F1 | 任何「一次处理 N 条」的地方都必须有 **N 的上界** 与「**失败只影响本块**」的语义 |
| F2 | 会让宿主事件循环同步阻塞、或加载原生库的操作，**不得留在主线程** |
| F3 | 重试必须同时有三个参数：**速率窗、次数上限、终局态**；缺一个就会变活锁或风暴 |
| F4 | 每条外部依赖调用都要有 **超时** 与 **降级路**；降级后行为必须比「干等」更接近正常 |
| F5 | 后台任务与前台请求共用资源时，必须有**明确的优先级判据**，不能靠调度巧合 |
| F6 | 任何「可能越界」的动作都要落至少一组数：**规模、耗时、生效预算、身份/运行时** |

## 3. 面与面的冲突（改任一旋钮前先读）

这一类回归绝大多数出在「**单看一个面合理、合起来越界**」。先立冲突表，再改参数。

| # | 冲突 | 常见错误裁决 | 正确裁决 |
|---|---|---|---|
| 1 | 字符帽 vs token 帽 | 用一个换算系数两边通吃 | **两个护栏，不许换算**。字符帽管传输/体积，token 帽管推理；中文按字符估 token 会低估数倍 |
| 2 | batch 越大越省调用 vs prompt 膨胀 | 把批提到很大 | 批有硬顶；碎片问题用「批前预收拢」解决，不靠加批 |
| 3 | 分块越多失败半径越小 vs 调用次数越多 | 碎到最小 | 按**规模预算**切 + 逐块容错；一整块失败不该连坐其余块，也不能碎到失去上下文 |
| 4 | 并发越高吞吐越好 vs 单飞 | 到处开并发 | 下游是单飞队列时，并发只会在同一队列堆活。并发只给真正独立的远端调用 |
| 5 | 单条快 vs 长批连续 | 全队列按优先级排 | 优先级**只对单条请求**生效；批仍追加队尾 |
| 6 | 熔断窗 vs 自愈窗重叠 | 自愈时顺手复位失败计数 | **不要复位**。复位会把「慢依赖」误判成健康，破坏背压 |
| 7 | 自愈要快 vs 毒输入活锁 | 整批重放 | **不整批重放**：ack 切片 + 速率窗；超过窗进显性终局 |
| 8 | 降峰 vs 时延 | 为降峰关掉高性能内存模式 | 先选零 infer 代价的降峰项；关内存池只作逃生手段（混合形状下时延可涨一倍以上） |
| 9 | 收紧上限 vs 配置树安全 | 用窄区间 schema 卡新值 | **宽外壁 + 代码内 clamp + warn**。窄 schema 会让已部署配置解析直接抛错，故障半径是整个配置树 |
| 10 | 观测越全越好 vs 观测自己变成规模问题 | 什么都记、永久留 | 保留期 + 条数上限。**观测面必须有界** |

## 4. 被反复否决的模式（别再试）

| 模式 | 否决理由 |
|---|---|
| 跑 N 轮就回收（recycle-on-N） | 若高水位是「见过的最大形状」的函数、不是计数累加器，回收收益≈0，代价是每次重启的加载时间。先量「同形状 N 轮是否蠕变」再谈 |
| 单纯降档（把上限调小） | 只缩输入不缩并发份数，对峰值几乎无效，还带来精度/覆盖率损失与口径混叠债 |
| 源头截断代替护栏 | 若护栏已覆盖崩溃面，源头截断零增益，只是先丢实质内容 |
| 用 `global.gc()` 之类的宿主手段回收原生内存 | 原生分配器持有的内存对 V8 不可见，证伪过就别再试 |
| 为自愈复位熔断计数 | 见冲突 6 |
| 用窄 schema 区间挡非法值 | 见冲突 9 |
| 把「无上界」当性能优化 | 没有上界的批不是快，是定时炸弹 |

## 5. 留痕清单（F6 最小集）

| 留什么 | 回答什么问题 |
|---|---|
| 每批的**实际规模**（token/字符/条数）+ 一个「不可证」哨兵值 | 这一批真正进了多少？哨兵（如 `-1`）比编造一个数诚实 |
| **生效预算**（而不是配置里的预算） | 这条产物是在哪个帽下生成的？（只记录，不进重算判据——否则一改参数就全量重算） |
| **身份与运行时**（pid / execPath / release.name） | 崩的是哪个进程、跑在 Electron 还是纯 node |
| 每次调用的**分层预算**与超时 | 哪一层在烧钱、哪一层在超时 |
| **降级/熔断/自愈事件** | 「刚才慢过」与「一直坏着」必须可区分 |
| 观测数据的**保留期** | 观测面不能自己变成规模问题 |

---

## 6. 落地顺序建议

1. **先 F6 后 F1**：不先留痕，改批大小无从判断是变好还是变坏。
2. **先 F3 后 F4**：没有终局态的自愈，会把熔断与退避的效果全部掩盖。
3. **F5 最后调**：优先级只在「前后台真的抢资源」时才有意义；先确认真的在抢。
4. **每次只改一个旋钮**，并把「改了什么、测出什么」写回冲突表——这一类事故的复发率与「没写回」强相关。
